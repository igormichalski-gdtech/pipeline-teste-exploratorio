QUALIDADE · TESTE EXPLORATÓRIO COM AGENTES

Como funciona o pipeline de teste exploratório

Agentes de IA usam o sistema como usuários comuns, com personas de baixa, média e alta habilidade, sem acesso ao código. Cada problema encontrado é reproduzido por outro agente antes de virar achado, e só então o código é consultado para apontar a causa.

PODE LER O CÓDIGO
1 · UMA VEZ POR PRODUTO

Preparar

Agente preparador · Opus
  • Lê README, docker e seed
  • Sobe o sistema local com banco e portas próprios
  • Desliga serviços externos (pagamento, WhatsApp, e-mail)
  • Cria um usuário por persona
  • Descreve os módulos em linguagem de usuário
Gera config.md e mapa do produto
2 · CADA EXECUÇÃO

Planejar

Orquestrador · Opus
  • Escolhe personas × missões
  • Missões dizem o quê, nunca como: "crie uma campanha para o Instagram da clínica"
  • Dados do jeito que as pessoas digitam: sem https, telefone com espaço
  • Não conta bugs conhecidos
Gera plano.md
3 · EM PARALELO

Explorar

Agentes-persona · Sonnet ou Haiku
  • Só ferramentas de navegador: nada de código, DevTools ou API
  • Segue o cartão: o que sabe e o que não sabe, paciência, dispositivo
  • Digita tecla a tecla e tira print de cada tela
  • Desistir é resultado válido
Gera achados brutos com prints
4 · CORTA FALSO POSITIVO

Verificar

Agente verificador · Sonnet
  • Refaz o passo a passo de cada achado duas vezes
  • Espera a tela carregar antes de concluir
  • Anota erros de console e rede
Confirmado · intermitente · descartado
5 · TRIAGEM

Triar

Orquestrador · Opus
  • Junta achados iguais entre personas
  • Acha a causa no código (arquivo:linha)
  • Tipo: bug, regra ruim, texto, layout ou falta de recurso
  • Severidade alta, média ou baixa
  • Compara com o histórico: novo, recorrente ou corrigido
Gera a lista final
6 · ENTREGA

Relatar

Orquestrador
  • Relatório só com bugs, cada um com o print logo abaixo
  • Tabela de missões com quem concluiu e quem desistiu
  • Consumo de tokens e custo por agente
  • Limpa os dados de teste
Gera relatorio.pdf e historico.md
↻ A próxima execução parte do histórico: prioriza o que mudou no git e os achados abertos, e marca o que foi corrigido.

Por que é desenhado assim

  • Sem código para a persona: se pedimos apenas "aja como leigo", a IA continua agindo como especialista. Com limites reais, ela tropeça onde o usuário tropeça.
  • Verificação separada: agentes de navegador acusam bugs que não existem quando a tela demora a carregar.
  • Missões com dados reais: é assim que aparece o erro que ninguém testou, como o "www.site.com" recusado.
  • Não substitui gente: encontra candidatos a problema de forma barata e repetível; a confirmação final é com usuários reais.

As personas (base: GenderMag + OCDE)

  • Carla, vendedora, nível 1, celular. Lê tudo, culpa a si mesma e desiste após 2 tentativas.
  • Rogério, gestor, nível 2, notebook. Lê só títulos e desiste após 3 tentativas.
  • Bruno, administrador, nível 3, desktop. Fuça, culpa o sistema e testa os limites.
  • Só 5% dos adultos estão no nível de quem desenvolve o sistema.
